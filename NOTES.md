# Notes: where the brief was unclear, wrong or missing something

(Earlier ports: history/*/NOTES.md. Add one line for every new place.)

- The brief says the image holds m68k-amigaos-gcc 6.5.0b; `amigadev/crosstools:m68k-amigaos` now holds gcc 16.2.1b. The kit skeleton and this port build and bench with it unchanged; nothing else noticed.
- `tools/bench.sh` gives a run `FRAMES / 25 + 60` seconds of wall time. A stock-machine bench of a game whose logic is slower than real time does not finish in that: 6,000 ticks of this game did not. The bench was shortened to 3,000 ticks (the brief's minimum) and the menus scripted faster so most of it is game play.
- The kit has no way to change the scroll position at a raster line, and the brief forbids writing a display list. This game changes the horizontal scroll at its sprite-0 split on two screens; the port draws the upper part's nametable columns into the rows above the split (whole tiles only), so a difference that is not a multiple of 8 pixels is rounded.
- The brief's sprite rules assume one picture per sprite; a NES game with 8x16 sprites and CHR-bank animation needs its own clustering and caching (src/video.c), and the 15-colour attached pairs limit how many clusters can overlap vertically (four, counting sprite 6).
- "Convert every asset on the host": the NES DMC samples are converted on the host (tools/dmc.py), but which samples a game plays has to be found by running it; the list is per game (tools/games/bnb.py).
- The brief does not mention a Kickstart ROM check beyond "real Kickstart: not verified". The user supplied Kickstart 3.1 (40.68); FS-UAE takes it with `--kickstart_file=` as an extra option of tools/bench.sh, and the bench gave the same checksum (not committed: copyrighted).
- The brief's "Measure after every milestone" gives whole-run numbers; the late frames of a NES port come from spikes (screen loads, camera cuts, CHR-bank animation), which only a per-frame log shows (tools/frames.py).
- As in the first port (history/llb/NOTES.md): the Amiga runs a 68k translation of the game, the host test the C translation of the same decoded program, not literally the same C; the equal checksum proves they agree. And src/sound.c writes Paula's registers directly (NES tone generation), outside ptplayer.
- "Keep the loop": with 60 ticks on a 50 Hz display every fifth frame needs two ticks. The loop is unchanged, but game_draw() runs the next tick in the frame's idle time and game_tick() then only counts it (same input as the loop would pass, so the checksum is unchanged). The brief neither allows nor forbids this.
- `late` counts vertical blanks without a new picture. A NES screen load runs for several frames with the NMI off; the port now ends the tick every 128 writes to $2007 there (as frames pass on the NES), so black frames are shown at 50 Hz meanwhile. The brief has no notion of a game whose own frames stop during loads.
- The brief's report template has no line for a second ROM (the user's Kickstart 3.1); it is mentioned under "Not done, not tested".
- A NES game's random-number generator can be stirred by its frame timing: any change to the frame model plays a different CPU-vs-CPU game from the same scripted input, so the bench's scenes have to be re-checked after each such change (field-play ticks counted on the host).
- The brief says "In a vasm file use `section gfx,data_c` and `incbin`" for chip RAM. With the current `amigadev/crosstools` image (gcc 16.2.1b toolchain) the linked executable has no chip flag on any hunk (checked in the hunk header), so such data loads into fast RAM when there is some: the port's DMC samples played as a click on a 4 MB fast-RAM machine and correctly on the stock one. `sys_chip_copy()` at load time works on both. The bench, the checksum and the screenshots cannot show this; only listening (or reading the hunk flags) does.
- The brief has no way to check sound on the emulator. FS-UAE's audio can be written to a file through OpenAL Soft's wave backend (`ALSOFT_CONF` with `drivers=wave`), without changing the kit's scripts: `tools/bench_audio.sh`.
- The kit has no way to narrow the display window, and the brief forbids an own display set-up. The port writes `DIWSTRT`/`DIWSTOP` (two registers, the window only: no fetch, modulo or sprite setting) from the kit's `sys_vbl_hook` at every vertical blank, after the kit's copper list set its 320-pixel window. Without it the columns that cross a NES picture's edge at a fine scroll had to be masked in software every frame, which cost more than any other display work. A `disp_window(x, w)` call in the kit would make this legal and simpler.
- The brief's blitter rule ("not faster than this CPU") holds even for work the CPU could leave to it: with the kit's `DMAF_BLITHOG` the CPU waits for chip RAM during a blit, so a blit only overlaps CPU work that stays in fast RAM.
- The brief's bench proves speed and equal checksums for the scenes the bench plays; for a translated game the code a player reaches (here pitching and batting in a 1-player game) is never run by a computer-against-computer bench, and untranslated code crashes. The brief has no step for it; this port fuzzes player input on the host (tools/fuzz_play.py) and translates what that reaches.
- Changing how many NES writes end a load slice changes the game the bench plays (the RNG follows frame timing), so speed numbers before and after are not comparable; the report gives both.
